# QEOS Database Consistency Report

**Status:** 🔴 FATAL MISMATCH DETECTED
**Date:** 2026-07-24

## Executive Summary
A code-to-database consistency verification was performed comparing the QEOS Multi-Tenant SaaS Infrastructure code (Supabase Repositories) against the human-supplied database schema audit (`aldhibani_` offline-first legacy database). 

**Conclusion:** The implemented codebase and the existing database structure are fundamentally incompatible. The code expects a normalized, multi-tenant enterprise schema, while the database consists of a flattened, single-tenant, legacy schema.

## 2. Aggregate Roots & Persistence Models

*   **Missing Persistence Models:** 16 out of 19 domain aggregate roots (e.g., `Organization`, `Branch`, `Supplier`, `PurchaseOrder`) have absolutely no persistence model in the existing database.
*   **Legacy Overlap:** Only `Product`, `SalesOrder`, and `Staff` have loose conceptual equivalents, but their structures do not match the domain aggregates.

---

## 3. Table Names matching Expectations

*   **Expected `products` vs Existing `aldhibani_products`**
*   **Expected `sales_orders` vs Existing `aldhibani_orders`**
*   **Expected `staff` vs Existing `staff_users`**
*   **Expected `users` / `roles` / `permissions` vs Existing `staff_users` (flattened JSONB)**

**Finding:** 100% Table Name Mismatch. The code will fail immediately upon attempting any query (`relation does not exist` errors).

---

## 4. Required Columns vs Existing Columns

The most critical discrepancy is Multi-Tenant isolation. 

*   **Code Expectation:** Every repository enforces `.eq('organization_id', organizationId.value)`. Many also enforce `branch_id`.
*   **Database Reality:** The `organization_id` and `branch_id` columns are **COMPLETELY MISSING** from all 8 existing tables.
*   **Result:** Even if table names were corrected, every query generated by the SaaS repositories would crash instantly due to missing tenant columns.

---

## 5. Primary Keys

*   **Code Expectation:** Strongly-typed UUID Value Objects (`OrganizationId`, `ProductId`).
*   **Database Reality:** Primary keys are defined loosely as `VARCHAR` or `VARCHAR / UUID`, often containing string prefixes like `HYB-XXXXXX` (as seen in `aldhibani_orders`). 

---

## 6. Foreign-Key Expectations

*   **Code Expectation:** Complex relational integrity (e.g., `inventory_items` referencing `branches` and `products`).
*   **Database Reality:** **ZERO** physical foreign key constraints exist in the supplied database. Relations are purely implicit/application-level.

---

## 7. Missing Columns Required by Implemented Code

To make the existing tables compatible with the implemented code, the following columns are missing:

*   **ALL Tables:** `organization_id`
*   **Operational Tables (`aldhibani_products`, `aldhibani_orders`):** `branch_id`
*   **`aldhibani_products` (to become `products`):** `code`, `cost`, `created_at`, `updated_at`. Existing columns are localized (`nameAR`, `nameEN`, `priceYER`) rather than standard multi-tenant shapes.
*   **`aldhibani_orders` (to become `sales_orders`):** `branch_id`, `created_by`. 
*   **`staff_users`:** Needs to be fully normalized into `users`, `credentials`, `roles`, `permissions`, `user_roles`.

---

## 9. Gap Analysis Conclusion

The QEOS implementation has been built for a highly normalized, B2B SaaS architecture using schema-driven data integrity and tenant isolation. 

The human-supplied database is a flattened, monolithic, offline-first application database belonging specifically to the "Aldhibani VIP" legacy system. 

**Code-to-Database Consistency is at 0%.** The system cannot function without either:
A. Generating and applying SQL migrations to create the missing QEOS SaaS schema on the database, OR
B. Rewriting the entire QEOS backend to conform to the legacy `aldhibani_*` structure (which would sacrifice all SaaS and multi-tenant capabilities).
